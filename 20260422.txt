RedisConfig 里把 value 序列化器设成了 StringRedisSerializer。
这意味着 Redis 存进去、取出来的值都是字符串。
Lua 脚本里用 tonumber(ARGV[1]) 来解析数字——tonumber 只能把 "100" 转成 100，
如果传进去的是 Java 序列化后的二进制字节（默认 JdkSerializationRedisSerializer）
tonumber 拿到的是乱码，返回 nil，然后整个算法就崩了。
所以 String.valueOf() 不是"防乱码"，是保证 Lua 能用 tonumber() 正确解析。
一句话记住：
Redis 值序列化用 String → 传参也必须是 String → Lua 里 tonumber() 才能工作

你漏掉的一步：扣之前要先判断库存够不够
你说的是"库存-1"，但如果库存已经是0了还-1，就变成-1了，这就是超卖。
所以 Lua 脚本的逻辑应该是：
1. GET 当前库存
2. 如果库存 <= 0 → 返回0（拒绝，已售罄）

为什么必须用 Lua？ 因为 GET 和 DECR 是两步，并发下两个线程都 GET 到库存=1，都认为可以扣，就都执行 DECR，库存变-1，超卖了。

方向对了，但有一个地方说反了，帮你纠正：

不是死信队列解决这个问题
死信队列是处理多次重试后仍然失败的消息，是兜底机制。
你描述的问题是：同一张票被重复落库两次，这叫重复消费，解决方案是幂等。

把你的思路补完整：
生产者生成 orderNo = AAA，发给Kafka
消费者第一次消费：
  → 落库，insert order where orderNo = AAA
  → 成功
消费者第二次重试（网络抖动/超时）：
  → 再次落库，insert order where orderNo = AAA
  → 如果有幂等保护 → 直接跳过，不重复插入  ✅
  → 如果没有幂等保护 → 插入两条一样的订单  ❌

  幂等怎么实现？ 消费者落库前先查：

  问题解决方案orderNo在消费者生成
