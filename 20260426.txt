今日暴露的设计问题与结论
问题一：定时任务职责混乱 原代码把监听器和定时任务复用同一个 doCancel()，导致定时任务也去做 Redis+1，但定时任务扫到的废单前提是监听器已经+1过了，重复+1导致库存虚增。
结论：监听器职责 = Redis+1 + MySQL DELETE。定时任务职责 = 只做 MySQL DELETE，不碰Redis。能被定时任务扫到的废单，一定是监听器已经+1但DELETE失败留下的，库存已经回补过了。
问题二：引入了不必要的复杂度 中途引入了 stock_returned 字段和"Redis宕机"场景，超出当前阶段需求，把逻辑搞复杂了。
结论：先实现最基础的链路，不过度设计。

抢票成功

  → MySQL创建订单(status=0, expire_time=now+15min)
  → Redis写入过期监听key(TTL=900s)

用户15分钟内支付
  → MySQL status=0→1，写pay_time
  → DEL过期监听key（切断回补链路）

用户超时未支付
  → 过期监听key TTL归零
  → OrderExpireListener收到事件
  → Redis库存+1（回补）
  → MySQL物理删除废单

主链路失败兜底（监听器+1成功，DELETE失败）
  → MySQL废单仍存在(status=0, expireTime已过)
  → OrderCleanupScheduler每5分钟扫一次
  → 直接DELETE废单（不碰Redis，库存已回补）
  → DELETE失败下次继续扫，直到成功

查重逻辑：status IN (0,1) 双拦截，物理删除保证放行。

二、今天遇到了什么问题
问题一：定时任务职责混乱，导致库存会被重复+1
最初的思路是：监听器和定时任务共用一个 doCancel() 方法，都执行 Redis+1 + MySQL DELETE。看起来复用得很干净。
但这是错的。
为什么会有这种情况：我当时只想着"两个地方都要取消订单，取消的动作是一样的，当然抽成一个方法"。这是典型的从代码结构角度想问题，
而不是从业务语义角度想问题。代码结构上两个地方做的事情"看起来一样"，但两个调用方处于完全不同的状态下：
监听器是第一次处理，Redis还没有+1；定时任务是第二次处理，监听器已经+1过了
，Redis库存已经回补过了。把两个不同前提下的操作写成同一个方法，就会在定时任务调用时多+1一次，导致 ticket:stock 的值比真实可售库存多1，产生超卖。
怎么解决的：把 cancelByListener 和 cancelByScheduler 拆成两个独立方法。监听器专用的执行 Redis+1 + MySQL DELETE；定时任务专用的只执行 MySQL DELETE，
明确不碰Redis。两个方法的名字就直接说明了调用方是谁、职责是什么，不会混用。
这个问题的本质是：复用代码不等于复用业务语义。两段代码在结构上相似，不代表它们的业务前提相同。以后在抽公共方法之前，先问一句：调用方的状态前提是否完全一致，如果不一致，就不该共用。

问题二：OrderExpireListener 里查 status=1 这个校验，乍一看是多余的
监听器只处理过期key，过期key对应的订单正常情况下 status 一定是0，为什么还要查一次MySQL确认？
当时我直接问出来了，觉得这是说错了。
但仔细想之后，这里藏了一个极端时序竞争场景：用户在第14分59秒支付，pay() 里调用 DEL key，但 DEL 指令进入网络还没到 Redis，同一时刻 key 的 TTL 自然归零，
Redis 先推出了 expired 事件，DEL 指令随后到达，发现key已经不在了，静默成功。监听器收到的是 TTL 归零产生的 expired 事件，它根本无法区分这是"超时未支付触发的过期"
还是"支付后DEL竞争产生的过期"。
如果没有 status 校验，监听器会误判为超时，执行 Redis+1，把已支付订单的库存又还回去一张，下个用户扣库存成功，票位已经卖给了前一个人，超卖就产生了。

查 status=1 这一步的作用不是"拦截已支付废单"，废单本来就不会是status=1。它的作用是：在DEL和TTL归零产生竞争时，
通过MySQL的真实状态来纠正监听器的误判。MySQL是最终一致的权威来源，
Redis的事件只是触发器，不能作为业务状态的唯一依据。
怎么看待这类问题：当一个校验看起来"多余"或"正常情况下不会触发"时，不要直接删掉，也不要直接保留，而是要先问：
有没有两个操作几乎同时发生、顺序错位的场景？如果有，这个校验很可能是在处理那个时序窗口，删掉之后在低概率的时序下会产生严重的业务错误（比如超卖）。


三、今天的心得
今天最大的收获是学会了怎么分析"看起来不可能的场景"。
在单线程、理想时序的思维模式下，很多校验确实是多余的，
逻辑上推导不出触发路径。但分布式系统里，两个操作之间永远存在一个时间窗口，任何在这个窗口里可能发生的事情，在足够高的并发量下，都会真的发生。
以前看到一段代码有"多余的判断"，第一反应是"这写重了"，
现在会先停一下，想一想：这里有没有并发操作在竞争同一份资源，如果有，这个窗口有多宽，在这个窗口里哪两个状态可能同时出现。
另外一个收获是：拆方法之前先想业务语义，不要只看结构相似。
cancelByListener 和 cancelByScheduler 代码结构上几乎一样，但调用它们的前提完全不同，强行复用就会在特定场景下出错。
好的方法拆分标准是"调用方的状态前提是否一致"，而不是"代码行数是否相似"。
