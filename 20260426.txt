今日暴露的设计问题与结论
问题一：定时任务职责混乱 原代码把监听器和定时任务复用同一个 doCancel()，导致定时任务也去做 Redis+1，但定时任务扫到的废单前提是监听器已经+1过了，重复+1导致库存虚增。
结论：监听器职责 = Redis+1 + MySQL DELETE。定时任务职责 = 只做 MySQL DELETE，不碰Redis。能被定时任务扫到的废单，一定是监听器已经+1但DELETE失败留下的，库存已经回补过了。
问题二：引入了不必要的复杂度 中途引入了 stock_returned 字段和"Redis宕机"场景，超出当前阶段需求，把逻辑搞复杂了。
结论：先实现最基础的链路，不过度设计。

当前最终正确逻辑（新对话基准）

抢票成功
  → Redis库存-1
  → MySQL创建订单(status=0, expire_time=now+15min)
  → Redis写入过期监听key(TTL=900s)

用户15分钟内支付
  → MySQL status=0→1，写pay_time
  → DEL过期监听key（切断回补链路）

用户超时未支付
  → 过期监听key TTL归零
  → OrderExpireListener收到事件
  → Redis库存+1（回补）
  → MySQL物理删除废单

主链路失败兜底（监听器+1成功，DELETE失败）
  → MySQL废单仍存在(status=0, expireTime已过)
  → OrderCleanupScheduler每5分钟扫一次
  → 直接DELETE废单（不碰Redis，库存已回补）
  → DELETE失败下次继续扫，直到成功

查重逻辑：status IN (0,1) 双拦截，物理删除保证放行。
